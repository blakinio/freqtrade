# Portal schema relation matrix

## Status and authority

- Production and staging schema authority: the ordered PostgreSQL migration manifest in `ai_platform/portal/control_plane/migration_authority.py`.
- Exact database contract: the normalized PostgreSQL contract generated by `ai_platform/portal/control_plane/schema_contract.py` and verified in the exact Portal image.
- ORM metadata is a runtime mapping and a deterministic table/column/type/nullability/primary-key validation source. The database migration contract remains authoritative for database-owned check, unique, foreign-key and index definitions.
- SQLite is limited to development and isolated tests. Every SQLite connection enables `PRAGMA foreign_keys=ON`; SQLite evidence is not accepted as production-dialect evidence.
- No relation in this document authorizes live-capital execution, withdrawals or protected production deployment.

## Classification rules

| Classification | Required behavior |
| --- | --- |
| `HARD_TENANT_FK` | The source tenant key and referenced identity are constrained together. Cross-tenant references fail at the database boundary. Deletion is `RESTRICT` unless a separately reviewed lifecycle proves another action safe. |
| `HARD_LOCAL_FK` | A durable relation inside one tenant-owned aggregate is constrained by the database. |
| `IMMUTABLE_EVIDENCE` | The identifier records who or what was observed at the time of an event. It is not rewritten or deleted merely because the current source record changes. |
| `EXTERNAL_PROVIDER` | The identifier belongs to an external exchange, identity provider, runtime or upstream control plane. Referential integrity is verified at the provider boundary and cannot be represented by a local database FK. |
| `SOFT_REJECTED_REFERENCE` | The target can legitimately be absent because the operation was rejected before target persistence. The relation is retained as immutable diagnostic evidence. |
| `SELF_IDENTITY` | The column is the row or aggregate identity and is protected by the table primary/unique key, not a foreign key. |

## Explicit non-FK references

| Source columns | Classification | Lifecycle and validation |
| --- | --- | --- |
| `portal_bot_command_idempotency_conflicts.attempted_command_id` | `SOFT_REJECTED_REFERENCE` | The attempted command may be rejected before a command row is created. It remains diagnostic evidence and must not be silently rebound. |
| Audit, identity-audit and session-revocation actor/principal/membership/correlation identifiers | `IMMUTABLE_EVIDENCE` | Historical attribution survives account, membership or session lifecycle changes. Authorization is enforced before the event is written; evidence is append-only. |
| `portal_audit_events.resource_id`, outbox aggregate IDs and event correlation IDs | `IMMUTABLE_EVIDENCE` | These identify the resource or causal chain observed at event time and are not cascade-deleted. |
| Exchange trade/order/position identifiers and `source_runtime_id` in operational read models | `EXTERNAL_PROVIDER` | The source runtime owns the identifier namespace. Import/reconciliation validates tenant and provider provenance; no local parent row is authoritative. |
| Identity-provider session IDs and OIDC flow inputs | `EXTERNAL_PROVIDER` | The OIDC provider owns the namespace. Tokens and raw secrets are not stored in schema evidence. |
| Telemetry model, feature-schema, runtime and source identifiers | `IMMUTABLE_EVIDENCE` or `EXTERNAL_PROVIDER` | Telemetry windows and drift assessments retain the exact provenance observed. Model versions that are locally promoted remain tenant-scoped through service authorization and the checked schema contract; external runtime/source identities cannot be local FKs. |
| Learning hypothesis insight IDs, candidate/experiment lineage and promotion-history actor IDs | `IMMUTABLE_EVIDENCE` | Experimental lineage and approval attribution must remain readable after source lifecycle changes. |
| Signal, strategy-lab and grid-configuration bot/experiment identifiers without a hard FK | `IMMUTABLE_EVIDENCE` | These rows preserve submitted/reproduced evidence. Service-layer tenant checks are mandatory; adding a hard relation requires a migration and an existing-data integrity preflight. |
| Primary aggregate IDs such as command, bot, snapshot, analysis, outcome, hypothesis and experiment IDs | `SELF_IDENTITY` | Protected by tenant-scoped primary or unique keys. They are not relations to another table solely because their names end in `_id`. |

## Tenant uniqueness rules

- `portal_decision_snapshots.trade_intent_id` is unique only in combination with `tenant_id`.
- Tenant-scoped identities may repeat in different tenants unless the owning contract explicitly defines a global namespace.
- Global uniqueness must never be inferred from a UUID-shaped string alone.
- Every new cross-table relation must classify tenant scope, deletion behavior, existing-data preflight and restore behavior before merge.

## Integrity and migration behavior

1. A migration that adds a hard relation first runs a non-destructive orphan scan.
2. Unknown or cross-tenant references fail closed. The migration does not delete or rewrite evidence automatically.
3. Repair or quarantine requires a separately reviewed, deterministic mapping that preserves original attribution.
4. The migration ledger stores ordered identity and SHA-256 checksums. Missing, pending, reordered, unknown or modified migrations fail readiness.
5. The checked PostgreSQL schema contract compares every table, column, type, nullability, default, primary key, unique constraint, check constraint, foreign key and index produced by the migration chain.
6. Backup and isolated restore acceptance must reproduce the same migration revision and normalized schema contract before restored data is accepted.
